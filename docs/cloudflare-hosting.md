# Cloudflare hosting

Current standalone target, reviewed 13 November 2026. The public landing/walkthrough and wallet-session login supersede the original owner-private Cloudflare pilot. This guide does not change the privacy of the separate original Sites deployment.

## Existing installation

Use the existing `porti-near` Worker, D1 database and configured build branch `cloudflare-standalone`; do not recreate resources to update documentation or recover data. `main` is the default source branch and can contain changes not yet deployed to the Worker. Confirm build SHA and final production deployment success before claiming a feature is live. Avoid carrying simulator keys from mainnet into testnet settings.

## New operator setup

1. Use Node **22.22.2+** and `npm ci`. Obtain the actual D1 database UUID and set build variable `PORTI_D1_DATABASE_ID`; `NODE_VERSION` should match the supported runtime. The database name generated by the script is `porti-near`, binding `DB`.
2. Configure build `npm run build:cloudflare`, deploy `npm run deploy:cloudflare`, root `/`, and the intended production source branch. The generated config sets `PORTI_HOST_MODE=cloudflare`, disables preview URLs and optionally adds R2 from build variable `PORTI_R2_BUCKET`.
3. Set stable runtime secret `PORTI_SETTINGS_KEY` privately, plus `PORTI_APP_URL` for the actual HTTPS origin. Preserve existing values on upgrades. Other integrations have separate [settings](setup.md).
4. Standalone defaults to **NEAR wallet sessions**: public landing/Try demo, authenticated private workspaces. An existing edge Access policy can still block visitors before application login. Change that policy only with the owner's explicit audience decision; never alter the original Site's owner-private access as part of a Worker update.
5. For an intentionally private Access deployment, explicitly set `PORTI_AUTH_MODE=access` with the correct `PORTI_ACCESS_TEAM_DOMAIN` and `PORTI_ACCESS_AUD`; validate JWT issuer, audience, expiry and the intended allowlist. Do not trust browser-supplied identity headers.
6. Deploy deliberately. The deploy script first applies **remote D1 migrations**, then uploads the built Worker. Back up data, inspect failures before retrying, and preserve additive migration history.

A clean clone can build with the README's dummy database UUID without provisioning anything. That UUID must never be used with the deploy command. This review does not provision resources, change billing or set runtime secrets.

## Data, attachments and recovery

D1 stores profiles, sessions, workspaces, social state, review/receipt records and USSD state. A new database is empty; Git does not back up that data. The old Sites database and credentials are not automatically migrated.

R2 is optional and must remain private. Enable it deliberately and set `PORTI_R2_BUCKET` so generated config binds `BUCKET`. Without it uploads remain unavailable. Configure a lifecycle rule deleting the `porti/` prefix after 90 days; read expiry alone is not physical deletion. Review usage/billing before provisioning on a zero-budget account.

Device wallet vaults belong to their browser origin. A changed hostname/device requires the user's encrypted backup and password. Restore locally through the wallet panel; never send a vault/private key to the server or AI. Backups do not include the transaction journal, so reconcile original pending hashes before new approvals.

## Telegram separation

`/api/porti/telegram/run` is disabled at the standalone gateway and route. The Worker does not inherit the original owner-private Site's schedule or service token. Bot settings and queue code exist, but unattended Worker delivery needs a separately authenticated runner and real acceptance. Never expose the old private updater to public visitors or invent a user identity to run it.

## Verify an update

Run the checks in [README](../README.md#verify-the-source). Verify the production build commit, public visit/demo, unauthenticated API denial, NEAR sign-in/session restoration, ownership isolation and migration compatibility. Provider setup, actual inference, two-user social access, Pocket carrier delivery and user-approved funded actions need separate evidence. Free-plan CPU, request and storage quotas still apply; no delivery SLA is claimed.
